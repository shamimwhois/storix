02

Why Storix?

Storage providers expose different APIs and capabilities. Large transfers introduce interruptions, duplicate requests, rate limits, partial writes, and uncertainty about data integrity. Storix centralizes those concerns behind a consistent Laravel API.

One stable API

Keep application business logic independent from provider-specific SDKs and response objects.

Resilient transfers

Persist sessions and chunk state so eligible transfers can recover after interruptions.

Integrity first

Verify chunks and final content with SHA-256 where bytes are available. Never infer success from metadata alone.

Laravel native

Integrate with the service container, queues, events, migrations, scheduler, cache, and filesystem.

03

Core concepts

Storage driver

A provider adapter implementing a provider-neutral contract. Each driver declares its capabilities and operational limits.

File metadata

Application-facing metadata and opaque identifiers. Physical provider keys stay private to infrastructure.

Transfer session

A durable workflow tracking intent, state, retries, ownership, and completion evidence.

Chunk

A bounded part of a transfer with an offset, expected size, state, checksum, and provider reference.

Capability model

Describes whether a driver supports streaming, range reads, multipart writes, atomic finalize, or pause/resume.

Idempotency

Allows safe request replay and duplicate detection without crossing tenant or owner boundaries.

07

Transfer lifecycle

Expected high-level lifecycle:

pending → preparing → transferring → verifying → completed
                     |               |
                     +--- retry_wait-+

Terminal states: failed · cancelled · expired
Optional state: paused (only where safely supported)
  • Validate authorization, limits, source metadata, and available temporary storage.
  • Create or reuse an eligible idempotent session.
  • Transfer chunks with bounded concurrency and persist verified progress.
  • Reconcile provider state after interruptions and retry only eligible failures.
  • Finalize through the driver and verify final integrity before marking complete.

See Transfer Engine for protocol and failure handling.

08

Security model

Authorization by scope

Every read, write, list, resume, share, and delete operation must enforce owner and tenant access.

Safe object keys

Generate opaque keys independently of user filenames; normalize paths and reject traversal.

Secrets stay private

Never expose provider tokens, signed URLs, private storage references, or raw exception traces.

Resource controls

Bound file size, chunk size, concurrency, queue attempts, quotas, and temporary disk usage.

Read the complete Security Design before implementing access or sharing features.

10

PHP API direction

The intended primary interface is PHP services/facade. Exact signatures and DTOs are subject to implementation and API review.

use ShamimStack\\Storix\\Facades\\Storix;

$file = Storix::files()->put(
    source: $uploadedFile,
    directory: 'invoices/2026',
    options: ['visibility' => 'private'],
);

$stream = Storix::files()->readStream($file->id);

$transfer = Storix::uploads()->start($source, [
    'directory' => 'backups',
    'idempotency_key' => $requestId,
]);

$status = Storix::transfers()->status($transfer->id);

See Core PHP API and REST API for suggested routes, response envelopes, and error conventions.

11

Configuration

Configuration is expected to cover default driver, driver credentials/settings, chunk policy, concurrency, retry policy, session retention, progress persistence, quotas, and optional REST adapter settings.

return [
    'default_driver' => env('STORIX_DRIVER', 'local'),
    'transfers' => [
        'chunk_size' => 8 * 1024 * 1024,
        'max_concurrency' => 3,
        'max_attempts' => 5,
    ],
    'api' => [
        'enabled' => false,
        'prefix' => 'api/v1/storix',
    ],
];

Values are illustrative only. See Configuration & Operations for the complete example and operational guidance.

12

Queues & operations

  • Use Laravel queues for long-running transfers.
  • Separate transfer and cleanup workloads when needed.
  • Use idempotent jobs, bounded attempts, locks, and worker timeouts aligned with queue retry settings.
  • Schedule stale-session recovery and temporary-resource cleanup.
  • Log sanitized structured fields such as transfer ID, driver, state, attempt, duration, and error code.

Redis may improve queue/progress workloads but should not replace durable relational metadata.

Frequently asked questions

Does Storix include a frontend or dashboard?

No. It is a backend-only package. Applications can build their own UI using the PHP API, events, or optional REST adapter.

Is Telegram required?

No. Telegram is an optional driver. The core architecture is provider-neutral, and Telegram Serverless is excluded.

Does every driver support pause, resume, and range downloads?

No. These behaviors depend on driver capabilities and execution mode. Storix must expose support explicitly instead of promising identical behavior for every provider.

Are all features implemented now?

No. This documentation describes the intended design and roadmap. Consult repository code, tests, and release notes for verified implementation status.

When is a transfer considered successful?

Only after the driver finalizes the object and the required integrity verification succeeds.
